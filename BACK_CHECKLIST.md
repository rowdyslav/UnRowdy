# Backend Template Checklist

Этот список нужен, чтобы довести текущий `backend` до состояния хорошего шаблона для хакатона. Разделение по приоритету: сначала исправить то, что влияет на безопасность, корректность и переносимость, потом улучшать удобство и масштабируемость.

## Must-Have

[] 1. Закрыть небезопасные mutation-эндпоинты авторизацией и проверкой владельца.
   Сейчас любой клиент может удалить пачку пользователей и услуг через `DELETE /users` и `DELETE /services`, а также редактировать и удалять чужие услуги через `PATCH /services/{service_id}` и `DELETE /services/{service_id}` без проверки владельца.

[] 2. Пересобрать auth-конфигурацию через env.
   `LoginManager("secret", "/auth/login")` сейчас использует захардкоженный секрет. Секрет токенов, TTL и связанные auth-настройки должны приходить из env, иначе шаблон небезопасен и непереносим.

[] 3. Починить Telegram auth-flow.
   `/auth/tg` сейчас доверяет голым `tgid` и `tgusername` из тела запроса и фактически позволяет привязать произвольный Telegram-аккаунт без верификации Telegram init data или подписи. Для шаблона нужен один реальный и проверяемый контракт авторизации через Telegram.

[] 4. Сделать сидинг категорий идемпотентным.
   В `lifespan` после проверки `if all_names == existing_names:` вызывается `yield`, но выполнение не прекращается. Из-за этого сидинг продолжает работать даже на уже заполненной базе, что ведет к дублям или падениям на unique-индексах.

[] 5. Убрать mutable defaults из моделей.
   В `User` поля `services` и `friends_ids` заданы через литералы списков и словаря на уровне класса. Для Pydantic/Beanie-шаблона безопаснее и предсказуемее использовать `Field(default_factory=...)`.

[] 6. Нормализовать публичные контракты чтения и фильтрации.
   `read_me_friends` и `read_one_friends` объявлены как `list[UserRead]`, но фактически могут вернуть `None` внутри списка для битых ссылок. Плюс `ServiceFind.min_price = 1` по умолчанию исключает бесплатные услуги, хотя модель `Service.price` допускает `0` и `None`.

[] 7. Вынести runtime-конфиг в env.
   Сейчас CORS origin'ы захардкожены в `main.py`, а backend-запуск зависит от конкретных localhost-адресов. Для шаблона origin'ы и прочие runtime-параметры должны задаваться через env и иметь понятные дефолты.

## Nice-To-Have

1. Убрать лишнюю связанность сидинга с приложением.
   Старт приложения сейчас не только поднимает БД, но и модифицирует данные. Для шаблона полезнее вынести сидинг категорий в отдельную команду, bootstrap-скрипт или контролируемый флаг.

2. Нормализовать response model'ы и возвращаемые типы.
   Сейчас часть хендлеров возвращает `Document` напрямую, часть `Read`-схемы. Лучше выбрать единый контракт и не светить внутренние Beanie-модели наружу.

3. Убрать N+1 и полные сканы из чтения данных.
   В сервисах и друзьях есть дорогие операции: загрузка всех услуг категории ради `category-maxprice`, отдельные `User.get(...)` в цикле, обход всех TG-пользователей для карты `service_id -> tg_username`. Для шаблона лучше сразу заложить более устойчивые запросы.

4. Развести роутинг категорий и услуг.
   Категории висят под тем же prefix `/services`, что и сами услуги. Для читаемого шаблона лучше либо отдельный router prefix, либо явная группа ресурсов без смешения.

5. Добавить минимальный набор backend-тестов.
   Сейчас нет smoke/integration-покрытия для auth, friend-flow, service CRUD и сидинга. Для шаблона хотя бы базовые API-тесты нужны, иначе регрессии в контрактах будут проходить незаметно.

6. Нормализовать ошибки и конфликты на уровне доменной логики.
   Например, регистрация сначала делает два отдельных запроса на уникальность, а затем вставку. Для шаблона полезнее опираться на уникальные индексы и единообразно превращать DB-conflict в HTTP 409.

## Optional

1. Ввести централизованный settings/config слой.
   Вместо разбросанных `env.str(...)` и хардкода удобнее иметь один `Settings`-объект с валидацией и типизированными полями.

2. Подготовить базу к миграциям и управляемому bootstrap.
   Если шаблон будет жить дольше одного хакатона, стоит добавить понятный путь для миграций Beanie/Mongo и начального наполнения данных.

3. Ослабить связанность с конкретной предметной областью.
   Категории услуг и Telegram-логика уже встроены в базовый слой. Если это именно шаблон, полезно постепенно отделять платформенные механики от предметных сущностей проекта.

4. Пересмотреть модель связей пользователя.
   `friends_ids` и `services` сейчас хранятся довольно грубо. Для шаблона можно выделить более чистые границы между профилем, дружбой, Telegram-связью и каталогом услуг.
